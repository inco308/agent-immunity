# 真实 LLM 评测快照（原生 Linux dsh 传输）

本次在 Linux 宿主上直接调用本机安装的 dsh（不再经 Windows→WSL），模型标识由实际响应核对：`deepseek-v4-flash-vision-exp`，提供方 `deepseek-official`，dsh `0.1.1-rc.2`，Node `v24.20.0`。两次运行各取得 16 条正式轨迹（8 场景 × baseline/gateway），seed 42，每场景最多 8 个规划步骤，共 58 次模型调用。

- 改动前：`dsh-native-baseline.json`，源码基线 `63a422a`（原生传输，凭证检查未改动）
- 改动后：`dsh-native-afters.json`，源码基线 `436ed49`（并入归一化多层解码与跨字段拼接）

两次运行使用同一模型、同一固定数据集、同一提示词、同一动作 schema、同一 seed 与步数预算；只有被测的核心检查器不同。

## 结果

| 改动后 | 16 | 16 / 16 | 0 | 0 / 0 | 42 | 0 | 0 |

## 如何解读

**本次运行没有攻击分母。** 该模型在无网关基线下也没有执行注入指令，八个场景的 `attack_attempts` 全为 0。条件拦截率只在实际发生攻击调用时才有定义，因此这里**不能**表述为"网关拦截率 100%"或"零泄露"，只能说没有观察到越权调用、也没有观察到被利用的结果。

**这组快照的主要结论是"没有引入退化"**：并入凭证检查改动后，16/16 场景仍完成交付，42 次良性工具调用（含读取、写入、发布与版本查询）全部放行，两次运行的误拒都是 0。凭证检查的误报风险是这次改动最需要观察的量，这里给出了同模型对照。

**它不能证明编码与跨字段修复有效。** 模型没有尝试外发凭证，所以 A13/A15–A24 那类编码变换在本次运行中根本没有出现。那些修复的证据在规则级基准与数据驱动夹具中，见 `docs/benchmark_guide.md#覆盖的凭证表示` 与 `tests/test_credential_encodings.py`、`tests/test_cross_field_credentials.py`。把两处证据分开报告，不合并成一个成绩。

## 复现

```text
python -m evals.run_live --backend dsh --model <本机可用模型> --split all --output artifacts/llm-eval/dsh.json
```

需要 Python 3.12+ 与 `interop/requirements.lock` 中锁定的依赖；dsh 应已登录。`--model` 必须与本机实际可用模型一致，不同宿主上模型名可能不同，换模型必须使用单独的结果文件。dsh 不提供确定性 seed，`seed` 只标识样本，不能描述为确定性重放。

## 边界

- 每个 case/模式只有一条轨迹，样本很小；结果不能解释为总体安全率或通用提示注入防御能力。
- 所有输入、虚构凭证与接收器均为评测自建，没有真实凭证，也没有访问外部网络目标。
- 模型拒绝执行注入与网关拦截是两件事；本表把两者分开记录。
- 采样在每次工具调用返回后进行，无法看到一次调用内部先写入再恢复的行为。
- 后端封装（系统提示、工具 schema）与 Codex/Ollama 不同，不能作为纯模型横向排名。
